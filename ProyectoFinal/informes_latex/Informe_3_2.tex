% ═══════════════ 1. AVANCE TÉCNICO ═══════════════
\section{Avance técnico}
A la fecha actual, el desarrollo del proyecto HostSigchos ha completado exitosamente su fase iterativa principal, logrando la estabilización de los siguientes módulos:
\begin{itemize}[label=\small\color{verdeO}$\blacksquare$]
    \item \textbf{Módulo de Autenticación:} Integración completa de Firebase Auth. Soporta inicio de sesión mediante Email/Contraseña, SSO con Google Sign-In, y validación biométrica local (Huella Dactilar y FaceID) usando Secure Storage.
    \item \textbf{Exploración Turística:} Integración del mapa con OpenStreetMap y \textit{Reverse Geocoding}, permitiendo a los usuarios visualizar el catálogo de hosterías mediante marcadores de geolocalización.
    \item \textbf{Flujo de Reservas:} Funcionalidad ``End-to-End'' habilitada, permitiendo al turista seleccionar fechas, habitaciones, agregar solicitudes al carrito y emitir una orden que queda con estado \texttt{pendiente}.
    \item \textbf{Panel Web (Sincronización):} Los propietarios pueden visualizar de manera instantánea (en vivo) las nuevas órdenes de reserva que se emiten desde la aplicación móvil.
\end{itemize}

% ═══════════════ 2. ARQUITECTURA APLICADA ═══════════════
\section{Arquitectura aplicada}
Para asegurar un ciclo de vida extenso y facilitar el trabajo colaborativo del equipo, se implementó rigurosamente \textbf{Clean Architecture} en conjunto con el patrón \textbf{Model-View-ViewModel (MVVM)}. 

\begin{itemize}[label=\small\color{verdeO}$\blacksquare$]
    \item \textbf{Dominio Aislado:} Las reglas de negocio (Entidades puras y Casos de Uso) no tienen dependencias externas. Esto significa que los \texttt{UseCases} (ej. \texttt{CrearReservaUseCase}) no conocen si la base de datos es Firebase, SQL o una API REST.
    \item \textbf{Patrón Repository:} Actúa como un ``puente'' entre la capa de Dominio (que define la interfaz) y la capa de Datos (que la implementa conectándose a Firebase). 
    \item \textbf{Inyección de Dependencias:} Empleando el paquete \texttt{GetIt}, se inyectan las instancias de los \texttt{Repositories} a los \texttt{UseCases}, y estos a los \texttt{ViewModels}. Esto es vital para poder realizar pruebas de simulación (Mocks) en el futuro.
\end{itemize}

% ═══════════════ 3. ESTRUCTURA DEL PROYECTO ═══════════════
\section{Estructura del proyecto}
El proyecto se dividió físicamente y de forma funcional en dos frentes, cada uno enfocado en un actor específico:

\begin{enumerate}
    \item \textbf{Aplicación Móvil (Flutter):} Consolidada en el directorio raíz. Contiene todo el front-end y lógica móvil dirigida exclusivamente al \textit{Turista}. Genera archivos .apk y .ipa.
    \item \textbf{Plataforma Web (React JS):} Alojada en un directorio separado (\texttt{HostSigchos-Web/}). Dirigida al \textit{Propietario} y al \textit{Administrador del Sistema}. Implementa un \texttt{AppContext} global que escucha los sockets de Firebase.
\end{enumerate}

Ambos frentes de desarrollo son totalmente independientes en código, pero comparten la misma instancia y base de datos (Backend as a Service) en la nube mediante \texttt{Firebase Cloud Firestore}.

% ═══════════════ 5. CÓDIGO PRINCIPAL EXPLICADO ═══════════════
\section{Código principal explicado}
Dos algoritmos principales sostienen la estabilidad de la herramienta:

\subsection{1. Algoritmo de Verificación de Disponibilidad (Solapamientos)}
El código más crítico se ejecuta en el \texttt{CheckDisponibilidadUseCase}. Cuando un usuario selecciona fechas (ej. 10 de Mayo al 15 de Mayo), el caso de uso realiza una consulta (query) a Firestore trayendo todas las reservas confirmadas o pendientes para una habitación. 
Luego, evalúa localmente el \textbf{solapamiento de intervalos}:
$$ \text{Se solapan si: } (CheckIn_{\text{nuevo}} < CheckOut_{\text{existente}}) \land (CheckOut_{\text{nuevo}} > CheckIn_{\text{existente}}) $$
Si la sumatoria de habitaciones ocupadas por reservas que se solapan excede la \texttt{cantidadTotal} de la habitación, el algoritmo la bloquea en la interfaz, previniendo el \textit{Overbooking}.

\subsection{2. Listeners Síncronos y Reactivos (Sockets)}
Para las notificaciones y el historial de reservas, no se usan consultas HTTP tradicionales (Pull). Se emplea la función \texttt{onSnapshot()} de Firestore a nivel de los repositorios. Esto abre un \textit{WebSocket} que escucha las actualizaciones del servidor, de modo que si un Propietario aprueba una reserva en la web, el documento muta en la nube e inmediatamente dispara la regeneración (notifyListeners) en el \texttt{ReservaViewModel} del celular del Turista, actualizando la pantalla sin intervención humana.

% ═══════════════ 6. BASE DE DATOS UTILIZADA ═══════════════
\section{Base de datos utilizada}
Para apalancar los requerimientos de tiempo real (Real-Time), se seleccionó \textbf{Cloud Firestore} provisto por Google Firebase. 
\begin{itemize}[label=\small\color{verdeO}$\blacksquare$]
    \item \textbf{Estructura NoSQL:} Los datos se organizan en ``Colecciones'' (ej. \textit{reservas}) y ``Documentos'' (JSON objects).
    \item \textbf{Seguridad Cero-Confianza (Zero-Trust):} Mediante el archivo \texttt{firestore.rules} se programaron políticas obligatorias donde un turista (usuario móvil) \textit{solo puede leer} y \textit{crear} reservas cuyo \texttt{usuarioId} coincida con su token JWT. Únicamente los administradores y propietarios tienen permisos de actualización de inventarios (precios, descripciones, cancelaciones masivas).
\end{itemize}

% ═══════════════ 8. PROBLEMAS ENCONTRADOS ═══════════════
\section{Problemas encontrados}
\begin{itemize}[label=\small\color{verdeO}$\blacksquare$]
    \item \textbf{Limitaciones de Geocoding y Mapas:} El uso excesivo de \textit{Reverse Geocoding} generó conflictos de cuota (Rate Limits) al momento de cargar el catálogo de hosterías. Se requirió implementar \textit{debouncers} e inicialización diferida (Lazy loading) para el mapa de OpenStreetMap.
    \item \textbf{Sincronización de Estado Complejo:} Durante el flujo de Checkout de múltiples habitaciones en el carrito, se detectaron excepciones asíncronas cuando se interrumpía abruptamente la conexión a la red antes de finalizar los registros \textit{batch} en Firestore, dejando reservas huérfanas. 
    \item \textbf{Reglas de Seguridad Estrictas:} Tuvimos múltiples errores de permisos denegados (Access Denied) en la fase inicial debido a que la interfaz web de propietarios no enviaba el JWT de autorización correctamente al intentar mutar inventario.
\end{itemize}

% ═══════════════ 9. MEJORAS PENDIENTES ═══════════════
\section{Mejoras pendientes}
\begin{itemize}[label=\small\color{verdeO}$\blacksquare$]
    \item \textbf{Automatización E2E:} Según la estrategia definida en la documentación del proyecto (\texttt{ESTRATEGIA\_PRUEBAS.md}), está pendiente la creación de Scripts E2E automatizados con \texttt{Patrol} para validar que ninguna actualización de interfaz rompa el proceso crítico de cobro.
    \item \textbf{Caché Offline-First:} Implementar la persistencia offline de Firestore, permitiendo a los turistas explorar las descripciones de hosterías y habitaciones que visitaron previamente, incluso sin señal de internet en zonas rurales de Sigchos.
    \item \textbf{Limpieza (Garbage Collection):} Refinar la función cron (Cloud Function) que depura las reservas abandonadas con más de 48 horas de antigüedad.
\end{itemize}
